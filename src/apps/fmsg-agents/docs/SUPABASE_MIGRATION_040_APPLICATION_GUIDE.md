## 1. How the pieces fit together

```
┌─────────────────────────────────────────────────────────────────┐
│  FMSG Agents app (Windows)                                      │
│  ├─ main process: agent-profiles.ts (CRUD, upload, validation)  │
│  │     └─ IPC → renderer (creation form, cards, picker)         │
│  ├─ run pipeline (agent-controller.ts)                          │
│  │     ├─ BEFORE RUN: validate agent profile + CV retrievable   │
│  │     ├─ TAILORING: extract CV text (in memory only)           │
│  │     └─ ATTACH: download ORIGINAL CV → upload to job form     │
└───────────────┬─────────────────────────────────────────────────┘
                │ session token (RLS = auth.uid())
┌───────────────▼─────────────────────────────────────────────────┐
│  Supabase project (nnebtygloqixibbjxsjr)                         │
│  ┌────────────────────────────┐  ┌─────────────────────────────┐│
│  │ public.agent_profiles      │  │ Storage bucket `agent-cvs`   ││
│  │ (new table, step 2)        │  │ (private, step 3)            ││
│  │  - id, user_id, name,      │  │  - objects at:               ││
│  │    target_job_title        │  │    <user_id>/<profile_id>/   ││
│  │  - cv_storage_path, ...    │──┼─▶    <uuid>.pdf|.docx        ││
│  │  - RLS: auth.uid()=user_id │  │  - policy: folder[1] =       ││
│  │  - GRANT anon, auth'd,     │  │    auth.uid() (step 4)       ││
│  │    service_role            │  │  - never public              ││
│  └────────────────────────────┘  └─────────────────────────────┘│
└─────────────────────────────────────────────────────────────────┘
```

- **`agent_profiles`** is the new source of truth for FMSG Agent profiles (name, target job title, CV metadata). It is deliberately separate from the website's `profiles` / `search_profiles` — the website keeps operating exactly as it does today.
- **`agent-cvs`** is a **private** bucket. The real CV file lives there; only the metadata (path, filename, mime, size) is stored on the row. The folder prefix `<user_id>/<profile_id>/` is what makes one profile unable to receive another profile's CV and makes ownership provable.
- **RLS + storage policies** are the security boundary: row access `auth.uid() = user_id`; object access `(storage.foldername(name))[1] = auth.uid()::text` and `bucket_id = 'agent-cvs'`. Even a signed URL is short-lived and only generated by the owning session.
- **App code** then only ever talks to these two resources; the run pipeline refuses to start without a retrievable CV and uploads the *original* file (never extracted text) when a form asks for an attachment.

**Website impact: none.** No website table, column, object or policy is altered.

## 3. Step 2 — Create the `agent_profiles` table (Migration 040)

**2a.** Create the table:

```sql
create table if not exists public.agent_profiles (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  name text not null default '',
  target_job_title text not null default '',
  cv_storage_path text,
  cv_filename text,
  cv_mime text,
  cv_size_bytes bigint,
  cv_uploaded_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

**Verify:**

```sql
select column_name, data_type, column_default
from information_schema.columns
where table_schema = 'public' and table_name = 'agent_profiles'
order by ordinal_position;
```

Expected: 10 columns as above.

**2b.** Enable RLS:

```sql
alter table public.agent_profiles enable row level security;
```

**Verify:**

```sql
select relname, relrowsecurity from pg_class
where relname = 'agent_profiles';
```

Expected: `agent_profiles | true`.

**2c.** Create the four ownership policies (one statement each):

```sql
create policy "agent_profiles_select_own" on public.agent_profiles
  for select using (auth.uid() = user_id);
```

```sql
create policy "agent_profiles_insert_own" on public.agent_profiles
  for insert with check (auth.uid() = user_id);
```

```sql
create policy "agent_profiles_update_own" on public.agent_profiles
  for update using (auth.uid() = user_id);
```

```sql
create policy "agent_profiles_delete_own" on public.agent_profiles
  for delete using (auth.uid() = user_id);
```

**Verify:**

```sql
select policyname, cmd, roles from pg_policies
where schemaname = 'public' and tablename = 'agent_profiles';
```

Expected: 4 rows (`select`, `insert`, `update`, `delete`).

**2d.** Grant Data API access (mandatory — new tables no longer get automatic grants; without this, PostgREST returns permission-denied for **everyone**, including service_role):

```sql
grant all on table public.agent_profiles to anon, authenticated, service_role;
```

**Verify:**

```sql
select grantee, privilege_type from information_schema.role_table_grants
where table_schema = 'public' and table_name = 'agent_profiles';
```

Expected: each of `anon`, `authenticated`, `service_role` × (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) (plus the owner rows).

## 5. Step 4 — Storage ownership policies

Preferred path — SQL Editor (policies on `storage.objects`):

```sql
create policy "agent_cvs_select_own" on storage.objects
  for select using (bucket_id = 'agent-cvs' and (storage.foldername(name))[1] = auth.uid()::text);
```

```sql
create policy "agent_cvs_insert_own" on storage.objects
  for insert with check (bucket_id = 'agent-cvs' and (storage.foldername(name))[1] = auth.uid()::text);
```

```sql
create policy "agent_cvs_update_own" on storage.objects
  for update using (bucket_id = 'agent-cvs' and (storage.foldername(name))[1] = auth.uid()::text);
```

```sql
create policy "agent_cvs_delete_own" on storage.objects
  for delete using (bucket_id = 'agent-cvs' and (storage.foldername(name))[1] = auth.uid()::text);
```

**Verify:**

```sql
select policyname, cmd from pg_policies
where schemaname = 'storage' and tablename = 'objects' and policyname like 'agent_cvs%';
```

Expected: 4 rows.

**Fallback:** if the deployed Supabase version rejects this syntax, configure the same four rules in the dashboard **Storage → agent-cvs → Policies** editor (bucket-scoped, "folder[1] equals authenticated user id" semantics). Report which path you used so the record can be corrected.

## 7. Step 6 — End-to-end spot check (after the app code lands)

- Create a profile in the app → row appears in `agent_profiles` for your `user_id`.
- Upload a CV → object appears under `<your_user_id>/<profile_id>/` in `agent-cvs`; `cv_storage_path` etc. are set.
- A run with that profile passes validation; a profile without a CV is blocked with a clear message.

---

## 8. Rollback (if ever needed)

- Drop the bucket (delete objects first), then `drop table public.agent_profiles;` — both are additive and user-owned, so nothing website-side is affected. Policies are dropped with the table/bucket.
