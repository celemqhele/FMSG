# FMSG Agents — Observability, Independent Profiles & Ubuntu Runtime (investigation 2026-11-03)

Investigated the founder's four 2026-11-03 requests (Run Setup modal redesign, Run workspace space utilisation, independent agent profiles/CV, live-preview + Ubuntu runtime) and produced five blueprints (`BLUEPRINT-20261103-004..008` in `docs/blueprints/`) and five `PENDING` Pro assignments (`TASK-20261103-005..009` in `logs/EOT/deepseekprodelegation/`). This file records the verified root causes; it follows the earlier feature-update work in `src/apps/fmsg-agents/docs/context/fmsg-agents-feature-update-three-workstreams_2026-11-03.md` (screencast ACK rules, E-003-A closure) and extends it with the four new diagnoses.

## Root cause 1 — Run Setup modal is cramped (container-first sizing)

The modal was sized before its content: `.modal-card.run-setup-modal { max-width: 740px }` with a **three**-column grid (`1fr 1.35fr 1fr`), forcing the autonomy cards into ~90px columns, the profile list into a 220px `overflow-y: auto` scrollbox (nested inside a body that already scrolls), and 8–10px paddings throughout. The founder's reference is ~896px (`max-w-4xl`), two columns 7/12 + 5/12, dropdown profile selector, 92vh max height. Fix direction: `BLUEPRINT-20261103-004` — content-first two-column rebuild, body-level scrolling only, no logic changes.

## Root cause 2 — Run workspace wastes the bottom half and demotes the preview

- `.workspace-main` (flex column, `overflow-y: auto`) contains `.run-page-shell` which has `width: 100%; min-height: 0` but **no `flex: 1`/height** → the whole run page is content-height and the empty lower half of the screen is unused workspace space.
- `.matrix-log-column { flex: 0 0 40%; max-width: 42% }` permanently gives 40% of the width to the activity log; the preview gets ~58% in a side-by-side split (the founder reference is a tabbed workspace with a full-canvas preview).
- `.viewport-shot { object-fit: contain; object-position: top center }` pins the 16:9 image to the top of a taller monitor → dark dead space below it.
Fix direction: `BLUEPRINT-20261103-005` — tabbed workspace (Preview | Pipeline | History), compact header/toolbar, full-canvas centred preview, `flex`/`min-height: 0` chain fixed at every level, runtime-agnostic canvas.

**Status (2026-11-03T20:28:00+02:00):** implemented as `TASK-20261103-006` (`COMPLETED`, `PENDING_REVIEW`) in `renderer/components/LiveLog.tsx` + `renderer/design-system.css` — see `logs/EOT/argoneot/EOT-TASK-20261103-006_run-workspace-preview-dominant.md`. The height chain was the sole cause of the wasted bottom half: `.run-page-shell` needed `flex: 1 1 auto` (the old rule had only `min-height: 0`), after which the preview panel measured 77–87 % of the usable Run height at five viewports with `scrollHeight == clientHeight` at every harness preset. Two implementation traps worth remembering: (a) only the active tab panel is mounted, so a `Needs You` prompt must force the preview tab or a blocking prompt can be invisible; (b) `.workspace-main`'s padding/overflow had to be tightened for the Run view **only**, done with `.workspace-main:has(> .run-page-shell)` so the other seven screens keep their own spacing without touching `App.tsx`. `.viewport-footer-link` is shared with `App.tsx`/`BillingPanel.tsx`/`HomeView.tsx` and must never be deleted with the run-only footer rules.

## Root cause 3 — Live preview does not follow the active page

`agent-controller.ts` models "one page per run": `this.page` is set once at launch, `startScreencast()` attaches `newCDPSession(this.page)` once, and there is **no `context.on('page')` handler** — so tabs/popups opened by job sites are never tracked, `currentHost()` reads the original page's URL, and `placeAutomationWindowBehindApp()`/`focusAutomationBrowser()` pick the **first** page target (wrong tab for "Open in Chrome"). **RESOLVED by `TASK-20261103-007`:** active-page tracking implemented — `trackPages()` registers close handlers for the launch page AND every later page (the first probe run caught that the launch page's close event was initially unhandled — a real stale-preview bug), newest-created-wins promotion switches both the automation page and the screencast (serialised through a switch chain so stop/start never interleave), close-fallback and close-last handling emit truthful phases, and window commands resolve the active page's target **URL-first** with a remembered-target fallback. **Implementation traps recorded:** (1) the page-level CDP session cannot serve the Target domain in modern Chrome (`Target.getTargetInfo` errors) — resolve targets from the browser-level session via `Target.getTargets`; (2) while a fresh tab is still `about:blank`, keep the previous target id and let the URL-first resolver take over once the real URL is known; (3) `switchToPage` must respect `running`/`paused`/`screencasting` so an idle or paused runner never re-attaches streams. Verified by a 19-check real-Chrome probe (`recycle_bin/page-tracking-probe-2026-11-03.cjs`): navigation, new tab, repaint frames, target resolution, close fallback, close-last, disconnect state, stop cleanup — 19/19.

## Root cause 4 — `column search_profiles.cv_file_path does not exist` and agent profiles

Migration `supabase/migrations/009_cv_variations.sql` **dropped** `search_profiles.cv_file_path` (replaced by `cv_variations` jsonb). `agent-controller.ts:279` (`loadProfile`) still selected the dropped column → every run start errored. `App.tsx:2015` (`hasCv`) read the same dropped column → CV status silently always false. The fix is architectural, not a column re-add. **RESOLVED (code) by `TASK-20261103-008`, commit `f8b99a0`:** `BLUEPRINT-20261103-006` implemented end-to-end — new `agent_profiles` table (migration 040, additive, RLS `auth.uid() = user_id`, `GRANT ALL ... TO anon, authenticated, service_role` per the Oct-30-2026 PostgREST change), private `agent-cvs` bucket with `<user_id>/<profile_id>/<uuid>.<ext>` paths, three-input creation flow, original-file CV usage for tailoring + attachments (in-memory, no temp files), run validation gate. The run pipeline no longer reads `search_profiles` at all; the account-level `profiles` read is retained for contact fields (documented decision). **Implementation traps recorded:** (1) untyped `mammoth`/`pdf-parse` packages — use lazy `require` as `any` at the point of use, not `declare module` augmentation; (2) `ui:flows` asserts the Profiles H1 ("Search Profiles" → "Agent Profiles") — copy renames require the harness expectation to move with them; (3) the agent `package.json` gained its own lockfile on first `npm install`. **Still founder-gated:** migration 040 + `agent-cvs` bucket application (`docs/SUPABASE_MIGRATION_040_APPLICATION_GUIDE.md`) before live-DB verification.

## Root cause 5 — no isolated runtime exists (strategic gap, not a defect)

Current runtime = external Windows Chrome + CDP screencast. The founder's vision (watch the agent operate a real computer) may warrant an FMSG-managed Ubuntu VM runtime. `BLUEPRINT-20261103-008` stages this: Phase 1 read-only host capability detection → founder approval gate → Phase 2 measured prototype (options A–D, same-session proof, full measurement matrix) → Phase 3 custom-appliance assessment + recommendation. **No host-level changes without founder approval; no production replacement yet.**
**Phase 1 DONE (2026-11-03/04):** report committed at `docs/HOST_PREREQUISITES_REPORT_2026-11-03.md`. Machine: Windows 11 **Home** build 26300 → no full Hyper-V; virtualisation **available** (WSL2 + Ubuntu distro running is the proof; CIM VT flags are masked by the active hypervisor — `systeminfo` confirms "A hypervisor has been detected"); 15.7 GB RAM, 119.6 GB free, iGPU only; Docker/VirtualBox/QEMU absent; `HypervisorPlatform` (WHPX) present but Disabled (enable = admin + restart); `VirtualMachinePlatform` Enabled. Harness trap recorded: `Get-WindowsOptionalFeature` rejects an array of feature names (parameter binding) — query individually. Phase 2 founder gate: Docker Desktop install (admin) for B/C; Ubuntu 26.04.1 ISO + VirtualBox install (admin) **or** WHPX enable (restart) for D.
**Phase 3 appliance candidates (founder Q&A, 2026-11-03):** the founder asked about super-light "mostly browsing" distros. Literal candidates assessed: ChromeOS Flex (Google product, Crostini friction — rejected), Porteus Kiosk (~150–400 MB, read-only locked browser — wrong for automation tooling), Peppermint OS (web-centric Debian desktop — cruft we'd strip). Decision: the appliance does not need a desktop distro at all — the required stack is Xvfb + openbox + Chromium + Node/Playwright + KasmVNC + shell tools, which on **Ubuntu Server (minimized)** lands ≈1.5–3 GB installed / ~2 GB RAM (keeping the Ubuntu 26.04 LTS base), or **Debian bookworm-slim** ≈1–2 GB (Playwright's official image lineage). **Alpine** (≈150 MB) skipped: musl-libc Chromium/Playwright compat friction. Keep the full Ubuntu Desktop VM as the reference implementation; build the appliance from the minimal base with documented scripts; all sizes approximate — measured in Phase 2, never quoted as fact before then.
